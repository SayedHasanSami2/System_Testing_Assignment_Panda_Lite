1.  **Test Plan**

## This test plan shows the inputs that were chosen the results that were expected and the HTTP status codes that were expected for the endpoints and behaviors of the Panda-Lite system that is being tested. The approach to testing is based on the API behavior described in documentation.md. The focus is, on making sure the functions work properly checking the authentication looking at role-based authorization understanding ownership rules following the order lifecycle transitions handling cancellation and rating limits applying filters, sorting data checking input validation and testing edge-case behavior.

## 1.1 Authentication APIs

### 1. Registration

**Endpoint:** POST /auth/register

#### Input / Parameter Choices

-   Valid username, email, password, and role

-   Customer registration

-   Restaurant user registration

-   Rider registration

-   Duplicate email

-   Duplicate username, where applicable

-   Missing username

-   Missing email

-   Missing password

-   Missing role

-   Invalid email format

-   Empty-string inputs

-   Invalid or unsupported role

-   Boundary and malformed input values

#### Expected Output & Status Code

-   Valid user registration → **201 Created**

-   Duplicate account information → **400/409**, according to documented behavior

-   Missing required fields → **400 Bad Request**

-   Invalid email format → **400 Bad Request**

-   Invalid role → **400 Bad Request**

-   Empty required fields → **400 Bad Request**

### 2. Login

**Endpoint:** POST /auth/login

#### Input / Parameter Choices

-   Valid registered email and password

-   Unregistered email

-   Incorrect password

-   Missing email

-   Missing password

-   Empty email or password

-   Invalid authentication credentials

#### Expected Output & Status Code

-   Valid credentials → **200 OK** + authentication token

-   Invalid credentials → **401 Unauthorized**

-   Missing required fields → **400 Bad Request**

## 1.7 Authorization, Permission, and Ownership Coverage

The test suite explicitly covers role-based access control and resource ownership.

The following roles are exercised:

-   Customer

-   Restaurant owner

-   Rider

Authorization tests verify that users can perform only the operations permitted for their roles. Ownership tests additionally verify that a valid user cannot modify resources belonging to another user or restaurant.

The suite therefore includes:

-   Customer attempting restaurant creation

-   Rider attempting restaurant creation

-   Non-owner restaurant user modifying another restaurant

-   Customer modifying restaurant information

-   Rider modifying restaurant information

-   Customer creating menu items

-   Non-owner restaurant owner creating menu items

-   Non-owner updating menu items

-   Customer updating menu items

-   Rider updating menu items

-   Unauthorized order lifecycle operations

-   Rating another customer\'s order

Expected authorization failures generally return **403 Forbidden**, while missing or invalid authentication credentials return **401 Unauthorized**.

## 1.8 Filter, Sort, Validation, and Edge-Case Coverage

The menu and order-related APIs are tested using boundary values and malformed inputs to identify validation and business-logic defects.

The test suite includes:

-   Zero price

-   Zero stock

-   Positive stock

-   Negative price

-   Negative stock

-   Missing required fields

-   Empty request bodies

-   Invalid IDs

-   Non-existent resources

-   Invalid filter fields

-   Missing filter values

-   Invalid sort directions

-   Available/unavailable menu items

-   Exact numeric filtering

-   Duplicate operations

-   Invalid order state transitions

-   Operations on completed or cancelled orders

These tests are intended to verify that the API does not merely return the correct HTTP status code but also enforces the underlying business rules.

## 1.9 Authentication and Security Coverage

Authentication behavior is tested across protected endpoints using:

-   Valid bearer tokens

-   Missing tokens

-   Invalid tokens

-   Expired tokens

-   Tokens belonging to different roles

-   Tokens belonging to users who do not own the target resource

A missing or invalid authentication token is expected to result in **401 Unauthorized**, while a valid authenticated user attempting an operation outside their role or ownership permissions is expected to result in **403 Forbidden**.

## 1.10 Defect-Oriented Testing

During execution, test results are compared against both the expected HTTP status code and the expected response/business behavior. A test is considered failed when either the HTTP response or the documented business rule does not match the expected behavior.

For example, during menu testing, a menu item was observed with:

stockQuantity = 0

isAvailable = true

while the expected business rule requires an item with zero stock to become unavailable. Although the API returned **200 OK**, the test is considered **FAIL** because the response violated the expected business logic.

All confirmed defects are documented separately in the **Defect Reports** section using the corresponding \_lab.requestId as the evidence identifier.
